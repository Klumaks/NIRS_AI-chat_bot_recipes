# Архитектура и границы компонентов

Статус: фактический Python-поиск, реализованный фронтенд с HTTP-моками и целевая серверная архитектура. Фронтенд: React + TypeScript + Vite, Tailwind CSS, React Router, TanStack Query, React Hook Form и Zod. Сервер планируется на FastAPI; БД, библиотека сессий и провайдер LLM остаются открытыми решениями серверной интеграции; см. [следующие шаги](../../README.md#следующие-шаги).

## Что существует

В `D:\ai-chef\ai-chef` находятся Python-модули подготовки корпуса, предобработки, собственного BM25, консольного поиска, тесты и benchmark. `app` содержит JSON-примеры, а не веб-приложение. Настоящий сервер и вызовы LLM отсутствуют. В frontend/ реализованы пользовательские и административные страницы, имитация аккаунтов и истории через MSW/IndexedDB.

## Целевая схема

```text
Гость -> регистрация / вход -> серверная сессия
                                  |
Веб-чат -> сервер: сессия и роль
             |
             +-> продукты -> предобработка -> BM25
             |                -> проверенный набор -> фильтры -> карточки
             |
             +-> выбор recipe_id -> проверенные состав и шаги -> рецепт
             |
             +-> вопрос -> выбранный рецепт + текущий диалог -> LLM -> ответ
             |
             +-> события и диагностика -> админка (только admin)
```

Общий путь продукта: «интерфейс → сервер → BM25 → проверенные данные → LLM → ответ». При этом LLM вызывается для уточняющих ответов, а карточки и рецепт возвращаются из проверенных структурированных данных. Фильтры вычисляются сервером, не моделью.

## Компоненты и хранение

| Компонент | Ответственность | Данные |
| --- | --- | --- |
| Веб-интерфейс | Доступ, чат, карточки, фильтры, админские экраны | Состояние открытого сеанса |
| Сервер | Сессии, роли, валидация, подбор, контекст вопросов | Постоянные аккаунты и личные чаты до удаления пользователем |
| Retrieval | Нормализация, BM25, Python-контракт | Версионируемые корпус и индекс |
| Проверенный набор | Шаги, параметры, происхождение | Дополнения по версии корпуса и ID |
| LLM-адаптер | Инструкция, ограниченный контекст, вызов и ошибки | Ключ только на сервере |
| Наблюдаемость | События и этапы исполнения | 30 дней, без переписки |

Переписка сохраняется в базе приложения с привязкой к пользователю до явного удаления чата. История отделена от журнала активности: тексты запрещены в журнале, но необходимы в личном хранилище чатов. Условия обработки контекста провайдером LLM проверяются при его выборе.

## Подбор и проверенный набор

1. Сервер принимает продукты и создаёт принадлежащие пользователю постоянный `chat_id` и связанный с ним `selection_id`. Новый подбор других продуктов создаёт отдельный чат; пустой экран до отправки не сохраняется как чат.
2. Нормализует запрос для BM25 и отдельно сопоставляет названия ингредиентов для списка недостающего. `matched_terms` не годится как готовый список наличия: совпадение могло прийти из названия блюда.
3. Получает ранжированных кандидатов, пересекает их с активным проверенным набором. Не ограничивается первыми пятью глобальными результатами до пересечения. Для малого набора допустима полная выдача `k=None` внутри сервера, без передачи её в LLM или браузер.
4. Добавляет проверенные параметры, применяет фильтры ко всем подходящим кандидатам, возвращает первые пять с сохранением относительного порядка BM25.
5. Повторная фильтрация использует весь подбор, а не только уже отображённые карточки. Новые продукты создают отдельный чат с новым подбором; прежние фильтры, рецепт и сообщения сохраняются в прежнем чате.

Дополнения не меняют исходный корпус задним числом. Связь: версия корпуса + `recipe_id` + URL. При пересборке ID могут измениться: требуется проверка или миграция соответствий.

У каждого дополнительного поля фиксируются источник, способ получения, проверяющий и дата. Если КБЖУ рассчитаны, описываются метод и масса готового блюда; произвольная оценка LLM не считается проверкой. Неизвестное остаётся `null`. Шаги обязательны для полного сценария, отдельные числовые параметры могут быть неизвестны.

## Вопросы по рецепту

Сервер проверяет владельца чата, подбора и диалога. В контекст входят только выбранный проверенный рецепт, ссылки и сообщения его активной ветки вопросов. Смена блюда создаёт новый conversation_id внутри того же chat_id; прежние сообщения сохраняются с привязкой к рецепту и не включаются в новую ветку автоматически. При ограничении контекста адаптер исключает старые сообщения, сохраняя рецепт и текущий вопрос. Точный лимит определяется перед интеграцией LLM по выбранной модели.

Инструкция модели: отвечать по контексту, не выдумывать числа и шаги, сообщать о недостатке данных. Качество проверяется отдельными сценариями; инструкция сама по себе не гарантирует корректность. Сбой LLM не закрывает доступ к рецепту.

## Авторизация и роли

Принято: email и пароль; регистрация всегда создаёт `user`; первый `admin` заводится серверной процедурой развёртывания без стандартного пароля. В админке можно создать аккаунт с ролью `user` или `admin`; сервер проверяет право вызывающего администратора и отклоняет неизвестную роль.

Сессия передаётся защищённой cookie, недоступной JavaScript; операции изменения состояния защищаются от CSRF. Пароли хранятся стойкими хешами. Конкретные библиотека, параметры хеширования, время жизни сессии и ограничения попыток входа выбираются перед серверной реализацией по официальной документации и фиксируются до реализации.

Роли и владение ресурсами проверяются сервером независимо от маршрутов UI. Выход и истечение сессии закрывают доступ и очищают локальное состояние, но сохраняют личные чаты. После нового входа доступен их список; открытие чата восстанавливает сохранённое состояние. Администратор не получает доступ к переписке через журнал.

## Активность и диагностика

События: регистрация, вход, выход, административное создание аккаунта (с назначенной ролью), поиск, фильтрация, выбор рецепта, вопрос, удаление чата, добавление/импорт/редактирование/удаление рецепта и ошибка. Поля события: время UTC, ID пользователя (если известен), тип, статус, длительность и ID запроса.

Журнал не содержит паролей, токенов, исходного текста продуктов, сообщений и ответов. Диагностика показывает исполненные этапы и длительности, фактический режим нормализации, версии корпуса/индекса, ID найденных и выбранного рецептов, признак вызова LLM, имя модели и безопасный код ошибки. Неиспользованные этапы явно обозначаются.

Диагностика наблюдает за интеграцией. Добавление данных вынесено на отдельную административную страницу /admin/rag; управление LLM не входит в этап. События очищаются через 30 дней; период задаётся в UTC, UI отображает время с указанным часовым поясом.

## Режимы и ошибки

- **Реализовано:** отдельный поисковый модуль.
- **Демонстрация:** локальный макет с фикстурами, добавленными деморецептами и деморолями.
- **Запланировано:** серверный продукт с авторизацией и LLM.

Пустая выдача — успешный результат; недоступный индекс — ошибка поиска; неизвестный параметр — неполнота данных; недоступная модель — ошибка ответа. Интерфейс игнорирует запоздалый ответ старого подбора по ID. Контракты — в [API](contracts.md).

## Постоянная история чатов

Предлагаемая модель: чат принадлежит user_id и содержит название из первого запроса, время создания/последней активности, продукты, связанный подбор, фильтры, упорядоченные сообщения и активный conversation_id. Сообщения выбора и ответа связаны с recipe_id и версией данных. Для выбранных рецептов сохраняются снимки состава, шагов, параметров и происхождения, чтобы чтение истории не зависело от последующей пересборки корпуса.

После открытия сервер восстанавливает сохранённую активную ветку; ограничение размера промпта не удаляет сообщения из истории. Продолжение разрешено только при доступном проверенном контексте сохранённой версии. Если контекст больше не доступен для продолжения, возвращается состояние recipe_unavailable: история и снимок доступны для чтения, но новые вопросы по этому рецепту отклоняются с объяснением и предложением нового подбора. Нельзя молча связывать старый ID с другим рецептом новой версии корпуса.

Доступ к чтению, продолжению и удалению — только по совпадению user_id. Администратор не получает доступа к чужой истории из-за своей роли. Удаление атомарно удаляет чат и связанные сообщения/подборы/контексты из хранилища приложения; активные ответы не могут создать их заново. Секреты, Git и административные журналы не используются для хранения переписки. Политика резервных копий уточняется при выборе инфраструктуры и не должна обещать мгновенное удаление из сторонних систем.

BM25, корпус, индекс и RecipeSearcher не меняются. Хранение истории, загрузка снимков и контекста LLM — зона сервера и адаптера интеграции, ещё не реализованная в этом репозитории.

## Граница HTTP-моков

Текущий путь: страница → типизированные функции src/api/services.ts → fetch → MSW → IndexedDB → согласованный JSON. Это имитация сервера в браузере; собственный BM25 не вызывается. React-компоненты не импортируют фикстуры. TanStack Query хранит серверное состояние; формы и открытие панелей — локальное состояние компонентов.

src/mocks содержит фикстуры, обработчики, транзакционное хранилище, запуск и демопанель. Динамический импорт до рендера включается только VITE_ENABLE_MOCKS=true. VITE_API_BASE_URL задаёт базовый адрес (по умолчанию /api/v1). В API-режиме MSW отключён, неизвестные/недоступные запросы не заменяются фикстурами. Неизвестный API-маршрут в демо возвращает ошибку 501.

IndexedDB хранит аккаунты с солью и PBKDF2-хешем, сессии, личные чаты, продукты, фильтры, снимки рецептов и события. Операции изменения выполняются транзакционно; запоздалый ответ после удаления не создаёт чат заново. Выход отменяет запросы и очищает приватный кэш Query, но сохраняет историю. Проверка роли и принадлежности выполняется обработчиками также для admin; это не настоящая серверная защита.

При интеграции HTTP-перехват снимается, тот же API-клиент обращается к FastAPI. Сервер должен реализовать настоящие cookie/CSRF, роли, владение, БД, поиск и адаптер LLM. Удаление src/mocks требует удаления только загрузчика из main.tsx и worker/зависимости, не переписывания страниц. См. [запуск и переключение](../frontend-check.md#переход-на-fastapi).

Последний успешно открытый адрес чата/рецепта — локальное предпочтение навигации, отдельное для каждого user_id в localStorage. Здесь нет сообщений или данных рецепта; доступ по адресу по-прежнему проверяется HTTP API. «Новый подбор» не перезаписывает этот адрес, удаление соответствующего чата его очищает. Новые серверные маршруты не требуются.

## Восстановление HTTP-моков после остановки Service Worker

Браузер может остановить Service Worker и позднее запустить его заново без перезагрузки страницы. Поэтому одной регистрации MSW при старте недостаточно: его активный перехват нужно проверить перед очередной операцией.

В деморежиме src/mocks устанавливает обёртку fetch только для настроенного API-префикса. Перед запросами выполняется служебная проверка /__ai-chef-mock-health__, отвечающая только через MSW. Если перехват потерян, тот же worker останавливается и запускается через публичный API MSW, затем проверяется повторно. Параллельные проверки объединяются. Уже отправленный GET, получивший сетевой сбой или ответ не в JSON (например, HTML или 404 dev-сервера) вместо ответа моков, повторяется один раз после проверки восстановления; запросы записи автоматически не повторяются. История, аккаунты, сессии и деморежим не переинициализируются.

Проверочный адрес не является контрактом FastAPI. В режиме настоящего API модуль не загружается и обёртка отсутствует. Ошибки 400/401/403/409/503 от обработчиков передаются интерфейсу; записи POST не повторяются автоматически после отправки.

Регрессия: остановить worker через Playwright/CDP в открытом приложении; без перезагрузки перейти к пользователям, создать аккаунт, повторно остановить worker и открыть активность. Ожидаются данные моков, сохранённый новый аккаунт и отсутствие сетевой ошибки вместо выдачи.

## Каталог демо-RAG и совместимость

Admin → типизированный API → MSW с проверкой роли → транзакция IndexedDB. Каталог хранит полные деморецепты и номер версии, пополняется формой либо JSONL. Проверка импорта не пишет данные; подтверждение заново проверяет весь файл внутри транзакции, включая конфликты с текущим каталогом, затем назначает ID и увеличивает версию. Настоящего индекса здесь нет. События rag_add/rag_import содержат автора, count и corpus_version, без текстов.

Новый подбор сохраняет полный снимок кандидатов и свою версию во внутренних данных чата. Фильтрация, открытие рецепта и диагностика используют эту версию после последующих добавлений; внутренние кандидаты не передаются в GET чата. Снимок выбранного рецепта сохраняется как раньше. Старое kv-состояние дополняется каталогом/кандидатами без сброса сессий, аккаунтов и сообщений; устаревшее difficulty удаляется из ответов и происхождения. Полный сброс демо восстанавливает исходные фикстуры. Страницы не импортируют фикстуры; API-режим не подменяет отсутствующие серверные маршруты моками.

### Изменение и удаление каталога

PUT/DELETE административного рецепта проходят проверку admin и expected_version записи. Сравнение версии, валидация, поиск дубликатов (кроме самой записи), обновление/удаление, рост версии и безопасное событие выполняются в одной транзакции. Другие изменения каталога не конфликтуют, если сама запись не менялась. Счётчик next_id сохраняется независимо от текущего максимального ID, миграция учитывает каталог и сохранённые снимки. Удаление не освобождает номер для нового рецепта.

Кандидаты и выбранные рецепты существующих чатов не меняются: чтение, фильтрация и вопросы продолжаются по сохранённой версии. Снимки служебных деморецептов также сохраняются внутри чата и не выдаются в GET чата; новые подборы не восстанавливают удалённые фикстуры. UI переиспользует одну форму, подтверждает удаление и после успеха обновляет список/журнал; конфликт оставляет черновик до отмены или повторного открытия актуальной записи. Настоящая интеграция этих операций с BM25 — следующий серверный этап.
