# Контракты интеграции

Статус: Python-интерфейс существует отдельно. HTTP-контракты ниже реализованы в MSW для локальной демонстрации фронтенда; настоящий сервер FastAPI ещё не реализован.

## Существующий retrieval

`RecipeSearcher.search(query: str, k: int | None = 5, require_all: bool = False) -> list[dict]`.

| Поле результата | Тип | Фактическое значение |
| --- | --- | --- |
| id | int | ID записи данной версии корпуса |
| title | string | Название |
| ingredients | array | Объекты `name: string, amount: string или null` |
| url | string | Источник |
| score | number | BM25, округлён до четырёх знаков |
| matched_terms | string[] | Совпавшие нормализованные термы |

Контракт сохраняется. Не добавлять в него вымышленные шаги или числовые параметры. Сервер обогащает результаты отдельным адаптером; `id` в веб-ответе называется `recipe_id`.

## Общие правила предлагаемого API

Префикс `/api/v1`, JSON UTF-8. Серверная cookie-сессия, серверные проверки ролей и владельца. Времена ISO 8601 UTC; `request_id`, `chat_id`, `selection_id`, `conversation_id`, `message_id` — непрозрачные строки. Они не являются секретами или способом авторизации. Recipe ID — целое число в явно указанной версии корпуса.

Успех возвращает полезные поля и `request_id`. Ошибка: `{"request_id":"…","error":{"code":"…","message":"…"}}`. Пароли и токены в ответы и журналы не включаются. Пустая выдача возвращает 200 и `items: []`, не 404.

| Маршрут | Доступ | Вход | Успех |
| --- | --- | --- | --- |
| POST /auth/register | Гость | email, password | 201: user_id, email, role=user; затем отдельный вход |
| POST /auth/login | Гость | email, password | 200: user_id, email, role; установка сессии |
| GET /auth/me | Вошедший | — | 200: текущий user_id, email, role |
| POST /auth/logout | Вошедший | — | 204, завершение сессии без удаления истории |
| POST /selections | user, admin | products_text | 201: новый chat_id и подбор с пустыми фильтрами |
| GET /chats | user, admin | limit, offset | 200: только свои чаты, items и total |
| GET /chats/{chat_id} | Владелец | — | 200: сообщения и сохранённое состояние чата |
| DELETE /chats/{chat_id} | Владелец | — | 204: удаление чата и связанных данных |
| POST /selections/{id}/filter | Владелец | filters | 200: тот же подбор с новыми фильтрами |
| POST /selections/{id}/recipe | Владелец | recipe_id | 200: рецепт, chat_id и новый conversation_id |
| POST /conversations/{id}/messages | Владелец | message_id, text | 200: chat_id, message_id, answer, sources, status |
| GET /admin/users | admin | limit, offset | 200: items, total |
| POST /admin/users | admin | email, password, role (`user` или `admin`) | 201: user_id, email, выбранная role |
| GET /admin/activity | admin | from, to, user_id?, limit, offset | 200: события и total |
| GET /admin/requests/{request_id} | admin | — | 200: безопасная диагностика |

Публичный `POST /auth/register` не принимает назначаемую роль и всегда создаёт `user`. В `POST /admin/users` поле `role` обязательно и принимает только `user` или `admin`; неизвестное значение или отсутствие поля возвращает 400 `VALIDATION_ERROR`. Создание аккаунтов обеих ролей доступно только действующему `admin`; запрос обычного пользователя отклоняется с 403 `FORBIDDEN`. Email очищается от внешних пробелов и сравнивается без учёта регистра. Для входа используется общее сообщение об ошибке. Для моков пароль содержит от 8 до 128 символов. Правила и ограничения попыток входа настоящего сервера фиксируются перед его реализацией.

Пагинация административных списков: по умолчанию 50, максимум 100; `offset` от 0. Период активности — последние 30 дней по умолчанию. Выход 204 не содержит JSON. При чужом, удалённом или отсутствующем чате/подборе/диалоге — 404 без раскрытия владельца.

## Подбор и фильтры

Ответ подбора: `chat_id`, `selection_id`, `corpus_version`, `filters`, `items` (не более пяти), `total` (число после фильтрации), `request_id`. Продукты в первой версии передаются свободным текстом, не в граммах.

```json
{
  "filters": {
    "kcal": {"min": 0, "max": 200},
    "protein_g": {"min": null, "max": null},
    "fat_g": {"min": null, "max": null},
    "carbs_g": {"min": null, "max": null},
    "max_total_time_minutes": 30
  }
}
```

Запрос фильтрации целиком заменяет текущие фильтры; отсутствующая граница или `null` означает отсутствие ограничения. Пустой `filters: {}` сбрасывает всё. КБЖУ всегда на 100 г готового блюда. Числа конечные и неотрицательные, минимум не выше максимума; время — положительное целое. Границы включаются; `null` рецепта исключается при активном ограничении этого поля.

Фильтры применяются ко всему проверенному подбору до ограничения числа карточек, не только к пяти уже показанным.

## Целевая карточка и полный рецепт

| Поле | Тип | Источник / правило |
| --- | --- | --- |
| recipe_id, title, ingredients, url | int, string, array, string | Адаптация существующего поиска |
| description | string или null | Проверенное дополнение; при null — «нет данных» |
| nutrition_per_100g | object | kcal, protein_g, fat_g, carbs_g; каждое number или null |
| total_time_minutes | int или null | Проверенное общее время |
| difficulty | easy / medium / hard / null | Проверенная оценка |
| missing_ingredients | string[] | Сопоставление состава с продуктами пользователя сервером |
| provenance | object | Происхождение дополнительных полей |

Полный рецепт добавляет `steps: string[]`, `chat_id`, `conversation_id` и `request_id`; остальные параметры совпадают с карточкой. Шаги непусты для доступного полного рецепта. Отсутствующие количества ингредиентов остаются `null`. `score` и `matched_terms` нужны диагностике, в пользовательской карточке не обязательны.

В `provenance` ключи дополнительных полей (включая `steps` и каждое поле КБЖУ) ссылаются на записи `source_ref`, `method` (`source`, `calculation`, `editorial`), `checked_by`, `checked_at`. Для расчёта source_ref ведёт к сохранённой методике и исходным данным. Метка `editorial` подходит для проверенного описания/сложности, не является основанием произвольных калорий. Демо-фикстуры отдельно получают `data_mode: "demo"`; серверный рабочий ответ — `"verified"`. Пользовательская маркировка не должна скрывать деморежим.

## Вопросы

Сервер не доверяет переданному клиентом тексту рецепта: контекст загружается по выбранному рецепту сервером. `message_id` генерируется клиентом и повторно используется при повторе того же вопроса; сервер не добавляет второй экземпляр сообщения в диалог.

Ответ: `answer: string`, `sources: [{recipe_id, url, step_numbers: int[]}]`, `status: "answered" | "insufficient_context"`, `request_id`. Номера шагов начинаются с 1. При нехватке контекста answer объясняет ограничение; это успешный ответ 200. До выбора блюда conversation_id отсутствует и отправка вопроса недоступна. После открытия сохранённого чата сервер восстанавливает активную ветку, а не создаёт второй экземпляр старых сообщений.

## Активность и диагностика

Для события административного создания аккаунта дополнительно сохраняются ID созданного аккаунта и назначенная роль (`user` или `admin`), без пароля. Событие: `occurred_at`, `user_id` (или null), `event_type`, `status`, `duration_ms` (или null), `request_id`. Диагностика: версии корпуса/индекса, режим нормализации, ID кандидатов и выбранного блюда, модель/признак вызова LLM, список `stages` с именем, статусом и длительностью, безопасная ошибка. Нет полных запросов, промптов, ответов и секретов.

## Ошибки

| HTTP | Код | Смысл / действие |
| --- | --- | --- |
| 400 | VALIDATION_ERROR | Неверные поля/диапазон; исправить ввод |
| 401 | AUTH_REQUIRED / INVALID_CREDENTIALS | Вход отсутствует/истёк либо неверные данные |
| 403 | FORBIDDEN | Нужна административная роль |
| 404 | NOT_FOUND | Ресурс отсутствует или недоступен этому владельцу |
| 409 | EMAIL_EXISTS | Email уже зарегистрирован |
| 409 | RECIPE_UNAVAILABLE | Сохранённый контекст нельзя продолжить; переписка и снимок доступны для чтения |
| 409 | RECIPE_INCOMPLETE | Нет проверенных шагов; вернуть безопасную ссылку в поле error.source_url |
| 503 | SEARCH_UNAVAILABLE / LLM_UNAVAILABLE | Сервис недоступен; повторить с теми же параметрами |

Неполные шаги не заменяются генерацией. Остальные неизвестные параметры допустимы как `null`. Внутренний traceback не передаётся пользователю.

## Постоянная история: предлагаемые интерфейсы

GET /chats возвращает `items: [{chat_id, title, created_at, updated_at}]`, `total` и `request_id`. Название — очищенный первый запрос продуктов; порядок updated_at по убыванию. limit по умолчанию 50, максимум 100; offset от 0. Сам список доступен только вошедшему пользователю, включая администратора только для его собственных чатов.

GET /chats/{chat_id} возвращает `chat_id`, `title`, `messages`, `selection_id`, `products_text`, `filters`, `selected_recipe`, `conversation_id`, `resume_status` и `request_id`. До выбора рецепта selected_recipe и conversation_id равны null. `selected_recipe` содержит снимок данных, corpus_version и версию проверенного набора. `resume_status` — ready либо recipe_unavailable. Сообщения упорядочены и содержат message_id, role, text, created_at и связь с conversation_id/версией рецепта, если применимо. Сохранённые карточки и выборы представлены связанными данными подбора/рецепта, а не реконструируются из текста ответа модели.

Каждый подбор и разговор принадлежат постоянному chat_id; сервер определяет эту связь по ресурсам, а не доверяет чужому chat_id клиента. Новое сообщение обновляет updated_at. Повтор одного message_id в том же разговоре не дублирует вопрос и ответ. При выборе другого блюда старые сообщения остаются, активная ветка меняется.

DELETE /chats/{chat_id} вызывается после подтверждения в UI и возвращает 204 без тела. Подтверждение реализуется интерфейсом, защита доступа — сервером. Последующие запросы удалённого/чужого чата и его вложенных ресурсов дают 404. Выход и истечение сессии дают 401 для доступа до повторного входа, но не выполняют DELETE. Незавершённый запрос не должен восстанавливать удалённый чат. При recipe_unavailable новый вопрос возвращает 409 RECIPE_UNAVAILABLE; история остаётся читаемой.

Маршруты реализованы в обработчиках MSW для локального фронтенда. Настоящая серверная реализация, БД и вызовы LLM пока отсутствуют. Контракт отдельного Python-поиска остаётся прежним.

## Реализация в локальном макете

API-клиент frontend/src/api использует эти маршруты, credentials: include и типизированные ответы; страницы не обращаются к фикстурам. MSW обрабатывает /api/v1 с HTTP-статусами 200/201/204, 400, 401, 403, 404, 409, 503 и request_id в ошибках. Неизвестный API-маршрут возвращает 501. На некорректных фильтрах возвращаются ошибки валидации; роль публичной регистрации задать нельзя.

Ключевые группы: /auth/register, /auth/login, /auth/me, /auth/logout; /chats, /chats/:chatId; /selections, /selections/:selectionId/filter, /selections/:selectionId/recipe; /conversations/:conversationId/messages; /admin/users, /admin/activity, /admin/requests/:requestId. Точные методы и поля приведены в разделах выше и в frontend/src/api/services.ts.

Cookie демо-сессии не является HttpOnly-защитой сервера. request_id непрозрачен; демонстрационные этапы явно обозначены, вызовы BM25 и LLM не имитируются как реальные замеры. Диалоги и пароли не записываются в журнал активности.

Для подключения FastAPI сохранить контракты, отключить MSW и настроить базовый адрес/прокси, cookie и CORS согласно [инструкции](../frontend-check.md#переход-на-fastapi).
