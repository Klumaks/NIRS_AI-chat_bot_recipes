# RAG: корпус, индекс BM25, поиск и оценка качества

> Ответственный: **BM25 и RAG** (корпус, индекс, поиск, benchmark).
> Статус: корпус с КБЖУ, временем, описанием и шагами собран; поиск BM25 с ранжированием по покрытию
> запроса, фильтрами КБЖУ/времени и полем «Не хватает» работает из консоли и как Python-модуль;
> бенчмарк — 30 запросов с критериями, разметка не выполнена. Связка с LLM — зона «Интеграции».

## 1. Место модуля в системе

```
Пользователь ──> Интерфейс ──> Бэкенд ──> RecipeSearcher.select(query, k, filters)
                                   │              └─> карточки рецептов + total (JSON)
                                   ├─> RecipeSearcher.get_recipe(id) ──> рецепт с шагами
                                   └─> промпт: вопрос + выбранный рецепт ──> LLM ──> ответ
```

Модуль `rag/` отвечает за этап **Retrieval** и за данные рецептов: найти рецепты по продуктам,
отфильтровать по КБЖУ и времени, отдать карточку и полный рецепт. Генерацию ответа выполняет интеграция.

## 2. Корпус

| Параметр | Значение |
|---|---|
| Источник | датасет [d0rj/povarenok_recipes_detail](https://huggingface.co/datasets/d0rj/povarenok_recipes_detail) (HuggingFace, лицензия датасета Apache-2.0) — подробная выгрузка povarenok.ru |
| Исходные файлы | 2 parquet, 200 МБ → `python -m rag.convert_parquet` → `data/raw/povarenok_detail.jsonl` (154 158 строк) |
| После очистки | **153 848 рецептов** (−77 с < 2 ингредиентами, −233 дубликата) |
| С КБЖУ на 100 г | 150 190 (97,6 %) |
| С временем приготовления | 103 166 (67,1 %); 6 значений отброшено как ошибки ввода |
| С шагами | 119 366 (77,6 %) |
| С описанием | 153 843 (≈100 %) |
| Сложность | **в источнике нет** |
| Версия корпуса | `data/corpus_meta.json` → `corpus_version`, например `povarenok-detail-153848-20261015` |

Предыдущий корпус (`rogozinushka/povarenok-recipes`, 146 263 рецепта, только название и ингредиенты)
заменён, потому что в нём не было полей карточки интерфейса. Его CSV по-прежнему поддерживается
`rag/corpus.py` для сравнения.

**Права.** Лицензия Apache-2.0 относится к датасету; права на сами рецепты по правилам povarenok.ru
принадлежат сайту. Корпус используется в учебных целях, в карточке всегда есть ссылка на источник (`url`).

### Очистка и поля (`rag/corpus.py`)

| Поле карточки | Откуда | Правило |
|---|---|---|
| `title` | `title` | пробелы нормализованы |
| `description` | `description` | пустое → `null` |
| `ingredients` | `ingredients[{name, count}]` | `[{name, amount}]`; «Яйцо куриное» → «Яйцо» (иначе «куриное» даёт терм «курица»); повторы убраны |
| `url` | `page_url` | — |
| `categories` | `kroshki` | путь категорий сайта: «Супы → Борщ» |
| `tags` | `tags` | теги автора рецепта |
| `total_time_minutes` | `cooking_time` («40 минут») | целое; 0 или больше 30 суток → `null` |
| `portions` | `portions_count` | целое или `null` |
| `nutrition_per_100g` | `nae_value["100 г блюда"]` | `{kcal, protein_g, fat_g, carbs_g}`; все нули или физически невозможные значения (> 900 ккал, > 100 г нутриента) → `null` |
| `has_steps` | `cooking_steps` | есть ли шаги |
| шаги | `cooking_steps` | хранятся отдельно: `data/steps.jsonl` + `data/steps_offsets.json` |

Шаги вынесены из карточек: поиску они не нужны, а держать 200 МБ текста шагов в памяти сервера незачем.
`StepsStore` читает шаги одного рецепта по смещению в файле.

Удаляются записи без названия и с менее чем 2 ингредиентами; дубликаты — одинаковые название (без
регистра) и множество ингредиентов. `id` — номер рецепта в данной версии корпуса, не id сайта.

## 3. Документ

**Документ = один рецепт.** Текст документа для индекса = **название + категории + названия ингредиентов**.

- Ингредиенты — главный сигнал для запроса «из чего приготовить».
- Название и категории дают тип блюда («суп», «салат», «выпечка»). Категории добавлены вместе с новым
  корпусом: запрос «суп со свёклой и капустой» теперь находит борщи, а не «Соленую капусту со свеклой».
- Количества, описание и шаги не индексируются: они не помогают найти блюдо по продуктам, а шаги
  размыли бы вес ингредиентов (в шагах упоминаются посуда, действия, температура).

## 4. Предобработка (`rag/text.py`)

Один и тот же конвейер для документов и запросов (замечание 1.1 методички):

```
текст → нижний регистр, «ё»→«е» → токены по регулярному выражению [а-яa-z]+
      → удаление стоп-слов и токенов короче 2 символов → нормализация слова
      → замена синонимов → повторная фильтрация стоп-слов
```

| Этап | Решение | Обоснование |
|---|---|---|
| Регистр | всё в нижний | «Картофель» в названии и «картофель» в запросе — одно и то же |
| «ё» → «е» | да | написание непоследовательно («свёкла»/«свекла») |
| Токенизация | слово = непрерывная последовательность букв | ингредиенты — это слова; цифры и единицы не нужны; дефис разделяет слова: «лук-порей» → «лук», «порей» |
| Общие стоп-слова | 84 служебных слова | не несут смысла |
| Предметные стоп-слова | единицы (`г`, `мл`, `шт`, `ложка`…) и «обёртки» запросов (`приготовить`, `рецепт`, `блюдо`, `накормить`…) | «что приготовить из фарша и картошки» → «фарш картофель» |
| Нормализация | **лемматизация pymorphy3** (основной режим), запасной — стеммер Портера (Snowball) | см. ниже |
| Синонимы | 37 пар после нормализации: `картошка→картофель`, `помидор→томат`, `куриный→курица`… | пользователи пишут разговорно, справочник сайта — формально |

**Почему лемматизация.** Русский язык флективный: «яйцо / яйца / яиц / яйцами». Лемматизация даёт
настоящую начальную форму. Стеммер Портера отрезает окончания и ошибается: «печень» и «печенье» → «печен»,
«лосось» → «лос». Стеммер (`rag/stemmer_ru.py`, своя реализация Snowball) — запасной режим без
зависимостей и вариант для сравнения в бенчмарке: `none` / `stem` / `lemma`.

## 5. Индекс и ранжирование (`rag/bm25.py`)

Своя реализация, готовые поисковые библиотеки не используются (требование задания).

Обратный индекс: `postings: терм → [(документ, TF)]`, длины документов, `N`, `avgdl`, `IDF`.

```
IDF(t)     = ln(1 + (N − DF(t) + 0.5) / (DF(t) + 0.5))
BM25(q, d) = Σ_{t∈q} IDF(t) · TF(t,d)·(k1+1) / (TF(t,d) + k1·(1 − b + b·|d|/avgdl))
```

`k1 = 1.5`, `b = 0.75` — стартовые значения (середина рекомендованного диапазона и стандарт); подбираются
по сетке на бенчмарке. Длина рецептов различается сильно, поэтому нормализация по длине нужна.

**Переранжирование по покрытию запроса** (по умолчанию). Сначала рецепты, где совпало больше разных термов
запроса, внутри группы — по BM25. Причина: из-за нормализации по длине длинный рецепт, где есть все продукты
пользователя, проигрывает короткому, где есть только часть («помидоры, козий сыр и вино»). Чистый BM25 —
`rank="bm25"`; оба варианта сравниваются в бенчмарке.

**Фильтры** КБЖУ и времени применяются ко **всем** найденным рецептам до отбора top-k (как требует
`contracts.md`), поэтому `total` — число рецептов после фильтров.

**Производительность** (полный корпус, Python 3.10, режим stem): построение индекса — 18 с, словарь —
17 453 терма, avgdl = 19,9; загрузка корпуса и индекса — 6 с, около 1,5 ГБ памяти; поиск без фильтров —
23 мс на запрос, с фильтрами — около 0,13 с (сортируются все кандидаты).

## 6. Интерфейс для интеграции

```python
from rag.search import RecipeSearcher

searcher = RecipeSearcher.load()                     # один раз при старте бэкенда
page = searcher.select("курица, рис и лук", k=5,
                       filters={"kcal": {"min": None, "max": 200}, "max_total_time_minutes": 40})
items, total = page["items"], page["total"]
full = searcher.get_recipe(items[0]["id"])           # карточка + steps + corpus_version
```

- `select(query, k=5, require_all=False, rank="coverage", filters=None) -> {"items": [...], "total": int}`
- `search(...)` — то же, возвращает только `items`.
- `k=None` — все найденные; `require_all=True` — только рецепты со всеми продуктами запроса.
- `filters` — формат `contracts.md`: `kcal`, `protein_g`, `fat_g`, `carbs_g` — `{min, max}` на 100 г;
  `max_total_time_minutes` — целое. Границы включаются; `null` — нет ограничения; рецепт с неизвестным
  значением исключается, если по этому полю есть ограничение. Некорректные фильтры → `ValueError`.
- `get_recipe(id) -> dict | None` — карточка + `steps: list[str]` + `corpus_version`.
- `count(query) -> {"any": int, "all": int}`.

Поля карточки:

| Поле | Тип | Описание |
|---|---|---|
| `id` | int | id рецепта в данной версии корпуса (`recipe_id` в веб-API) |
| `title`, `description` | str, str \| null | название, описание автора |
| `ingredients` | list[{name, amount \| null}] | состав |
| `url` | str | ссылка на рецепт на povarenok.ru |
| `categories` | list[str] | категории сайта |
| `total_time_minutes` | int \| null | время приготовления со страницы рецепта |
| `portions` | int \| null | число порций |
| `nutrition_per_100g` | {kcal, protein_g, fat_g, carbs_g} — числа или null | КБЖУ на 100 г готового блюда, расчёт povarenok.ru |
| `has_steps` | bool | есть ли шаги для полного рецепта |
| `score` | float | BM25 |
| `matched_terms` | list[str] | совпавшие термы запроса |
| `missing_ingredients` | list[str] | продукты рецепта, которых нет среди названных пользователем («Не хватает»); базовые продукты (соль, вода, чёрный перец, растительное масло, специи, приправа, лёд) не выводятся никогда |

**Сложности (`difficulty`) в источнике нет** — интеграция передаёт `null`, интерфейс показывает «нет данных».

**Происхождение данных (для `provenance` в `contracts.md`).** КБЖУ — `method: "calculation"`, расчёт
калькулятора povarenok.ru по составу (`source_ref` — `url` рецепта и `corpus_meta.json`); время, описание,
шаги — `method: "source"`, данные автора рецепта на povarenok.ru. Вручную значения не проверялись —
это нужно явно отражать в `checked_by`.

**Как считается «Не хватает».** Ингредиент считается имеющимся, если хотя бы одно его значимое слово после
той же нормализации и синонимов, что и в поиске, есть в запросе: «Филе куриное» закрывается словом
«курица», «Сыр козий» — словом «сыр». Слова-уточнения («чёрный», «сладкий», «репчатый»…) не считаются:
«черный хлеб» не закрывает «Перец черный». Ограничение: «сыр» закрывает любой сыр.

Пример реального ответа — `app/demo_search_results.json` (4 запроса × 5 карточек + один полный рецепт).

## 7. RAG: как результаты попадают в LLM (предложение для «Интеграции»)

1. `select(user_message, k=5, filters=...)` → карточки; пользователь выбирает рецепт.
2. `get_recipe(id)` → контекст для LLM: название, ингредиенты с количествами, шаги (нумерованные), ссылка.
3. Инструкция модели: отвечать только по контексту рецепта, ссылаться на номера шагов, не выдумывать
   количества и шаги. Если `has_steps = false` — сообщить, что шагов в источнике нет, и дать ссылку.
4. Пустая выдача — ответ без LLM: «не нашёл, уточните продукты или ослабьте фильтры».

## 8. Оценка качества (`benchmark/`)

**Тестовый набор** — `benchmark/queries.json`, 30 запросов, равномерно по разделам корпуса (горячее,
рыба, супы, салаты, закуски, выпечка, десерты, завтраки, гарниры, макароны, овощи, соусы, напитки,
заготовки, постное). Запросы сформулированы как пишет пользователь (разговорные слова, «обёртки»,
отрицание «без яиц», запрос из одного слова), у каждого — критерий релевантности для разметчика.

**Разметка (pooling).** Для каждого запроса объединяются top-20 выдач нескольких вариантов системы
(`lemma`, `stem`, `none` × ранжирование `bm25`, `coverage`) → `benchmark/pool.csv`; разметчик ставит 1/0
по критерию; `make_pool --apply` переносит разметку в `queries.json`. Не меньше 3 релевантных на запрос.
Пул пересобран под новый корпус (1 048 пар); разметка старого пула к новому корпусу не применима.

**Метрики** (`benchmark/evaluate.py`): `Recall@k` (k = 5, 10, 20) и `MRR` по формулам методички.

**Эксперименты:** нормализация `none` / `stem` / `lemma`; ранжирование `bm25` / `coverage`; сетка `k1`/`b`.

## 9. Проверяемые требования к модулю

| № | Требование | Как проверить |
|---|---|---|
| R1 | Индекс BM25 реализован без готовых поисковых библиотек | `rag/bm25.py`; тест `test_bm25_formula_by_hand` |
| R2 | Запрос из 2–5 продуктов в свободной форме возвращает не менее 3 рецептов, содержащих хотя бы один из продуктов | `python -m rag.search query "..."` |
| R3 | Падежи и разговорные формы находят те же рецепты, что и формы справочника | тесты `test_normalizer_*` |
| R4 | Поиск без фильтров < 100 мс, с фильтрами < 500 мс на полном корпусе | замер: 23 мс / 0,13 с |
| R5 | Каждая карточка содержит ссылку на источник | поле `url` |
| R6 | Неизвестные КБЖУ/время не подменяются числами; фильтр исключает такие рецепты при активном ограничении | тесты `test_detail_parsing`, `test_filters` |
| R7 | Фильтры применяются до отбора top-k, `total` — число после фильтров | тест `test_filters` |
| R8 | Тестовый набор: ≥ 30 запросов, ≥ 3 размеченных релевантных на запрос; посчитаны Recall@k и MRR | `python -m benchmark.evaluate` (к КТ2) |

## 10. Известные ограничения

1. **КБЖУ — расчёт калькулятора сайта, не проверенные данные.** Встречаются внутренние противоречия:
   у «Баклажанов с грибами под сметаной» 62 ккал при Б 2 / Ж 3,3 / У 21,6 (по Б/Ж/У выходит ≈ 124 ккал).
   У 2,4 % рецептов КБЖУ нет.
2. **Время есть у 67 % рецептов**, у остальных — «нет данных»; при фильтре по времени они исключаются.
3. **Сложности в источнике нет.** Выводить её из времени или числа шагов значило бы выдумывать данные.
4. **Шагов нет у 22 % рецептов** — для них вопросы к LLM по шагам невозможны, только ссылка.
5. **Отрицание не поддерживается.** «печенье без яиц» → «яиц» повышает рецепты с яйцами. План: разбор «без X».
6. **Очень частые продукты дают слабую выдачу** («яйца и сахар» — десятки тысяч рецептов, низкий IDF).
7. **Стемминг склеивает разные слова** («печень»/«печенье») — довод в пользу лемматизации.
8. **Память:** корпус карточек ≈ 200 МБ на диске и ≈ 1,5 ГБ в памяти процесса. При нехватке памяти можно
   не держать в памяти описания и теги, а читать их по смещению, как шаги.

## 11. Как запустить

```bash
pip install -r requirements.txt pyarrow       # pymorphy3 — лемматизация; pyarrow — чтение parquet
# скачать 2 parquet-файла датасета d0rj/povarenok_recipes_detail в data/raw/
python -m rag.convert_parquet                 # parquet -> data/raw/povarenok_detail.jsonl
python -m rag.corpus data/raw/povarenok_detail.jsonl    # -> corpus.jsonl, steps.jsonl, corpus_meta.json
python -m rag.search build                    # индекс (иначе строится при первом поиске)
python -m rag.search query "курица рис лук" -k 5
python -m rag.search query "курица рис" --kcal :150 --max-time 40     # фильтры
python -m rag.search recipe 123               # полный рецепт с шагами
python tests/test_rag.py                      # тесты
python -m benchmark.evaluate --mode lemma --mode stem --mode none     # после разметки
```

Без скачивания можно проверить на выборке: `data/sample_corpus.jsonl` (2 000 случайных рецептов нового
корпуса, seed 42): `python -m rag.search query "курица рис" --corpus data/sample_corpus.jsonl`.
